# WMS Marketplace Integration

This project is a simple Warehouse Management System (WMS) built for a full-stack technical test. It integrates an internal warehouse workflow with a Marketplace Mock API while keeping marketplace-owned states separate from warehouse-owned states. The goal is to support a safe internal `pick -> pack -> ship` lifecycle without overwriting the marketplace lifecycle.

## Project Goals

This project is designed to:

- provide secure internal APIs for warehouse operators
- synchronize marketplace orders into a local database
- keep the internal WMS lifecycle separate from marketplace statuses
- ship orders through the marketplace so tracking numbers always come from the marketplace
- provide a minimal UI for login, order listing, order detail, filtering, and role-based actions

## Architecture Overview

The project is split into two applications.

### 1. Backend

- language: Go `1.22.2`
- HTTP framework: Fiber
- database: PostgreSQL
- data access: Bun
- internal auth: JWT

Backend responsibilities:

- internal user authentication
- role-based authorization
- marketplace order synchronization
- WMS status transition validation
- secure marketplace token storage on the server
- webhook handling for marketplace status updates

### 2. Frontend

- React + Vite + TypeScript
- TailwindCSS
- Zustand for local UI and auth state
- TanStack Query for server state

Frontend responsibilities:

- warehouse operator login
- order list and order detail screens
- filtering and pagination
- showing allowed actions based on order status
- disabling actions based on the user role extracted from JWT
- consuming the real backend API directly for all order and marketplace actions

## Domain Flow

### Status ownership

Following the technical test requirements, this project clearly separates ownership:

- `marketplace_status`: owned by the marketplace
- `shipping_status`: owned by the marketplace
- `tracking_number`: generated by the marketplace when shipping
- `wms_status`: owned by the internal WMS

### Internal WMS lifecycle

```text
READY_TO_PICK -> PICKING -> PACKED -> SHIPPED
```

Rules implemented in the backend service layer:

- `pick` is only allowed when the current status is `READY_TO_PICK`
- `pack` is only allowed when the current status is `PICKING`
- `ship` is only allowed when the current status is `PACKED`
- `ship` must call the Marketplace API first
- `tracking_number` is never generated by the WMS itself

### Order synchronization

When the order list endpoint is called for the first time and the `orders` table is still empty, the backend will:

1. fetch orders from the marketplace
2. filter orders that are eligible for WMS processing
3. persist the order and its items into the local database

In the current implementation, only marketplace orders with status `paid` are imported into WMS, and they start with the internal status `READY_TO_PICK`.

Design note:

In my view, the ideal WMS intake rule should be narrower: an order should enter WMS only after the marketplace status is already `paid` and the shipping status is still before `shipped`, for example such as `label created` or `awaiting pickup`. However, based on the sample order data provided in this test, the shipping state combinations did not feel consistent enough to enforce that rule safely. Because of that, the current implementation applies the simpler and more reliable rule that only orders with marketplace status `paid` are imported into WMS.

## Database Design

The schema is designed to separate transactional order data, order items, internal users, and marketplace OAuth tokens.

### `users` table

Stores internal operator accounts used for authentication.

Important columns:

- `email`
- `password`
- `role`

Allowed roles:

- `picker`
- `packer`
- `warehouseAdmin`
- `superAdmin`

### `orders` table

Stores the marketplace order snapshot together with the internal WMS state.

Important columns:

- `order_sn`
- `shop_id`
- `marketplace_status`
- `shipping_status`
- `wms_status`
- `tracking_number`
- `total_amount`
- `raw_marketplace_payload`
- `created_at`
- `updated_at`

Design notes:

- `order_sn` is unique to prevent duplicate imports
- `raw_marketplace_payload` is stored as `JSONB` for auditing and debugging
- a database constraint ensures that `wms_status` always stays within valid values

### `order_items` table

Stores normalized line items for each order.

Important columns:

- `order_id`
- `sku`
- `quantity`
- `price`

Relationship:

- `order_items.order_id -> orders.id`

### `marketplace_tokens` table

Stores OAuth token data on the backend.

Important columns:

- `shop_id`
- `auth_code`
- `access_token`
- `refresh_token`
- `expires_at`

Why this table is separated:

- marketplace credentials never reach the frontend
- tokens can be refreshed automatically before they expire
- the OAuth bootstrap flow stays traceable on the server

## Available APIs

### Auth

- `POST /api/auth/login`
- `POST /api/auth/register`

All internal order and marketplace endpoints require JWT, except public webhooks.

### Orders

- `GET /api/orders`
- `GET /api/orders/:order_sn`
- `POST /api/orders/:order_sn/pick`
- `POST /api/orders/:order_sn/pack`
- `POST /api/orders/:order_sn/ship`

Supported order list filters:

- `search`
- `wms_status`
- `marketplace_status`
- `shipping_status`
- `page`
- `limit`

### Public webhooks

- `POST /webhook/order-status`
- `POST /webhook/shipping-status`

Important behavior:

- webhooks do not require JWT
- marketplace and shipping statuses update the local order record
- terminal marketplace events are ignored when they try to overwrite an existing terminal state
- a `paid` webhook for an order not yet stored locally can trigger a sync from the marketplace

### Marketplace integration helper endpoints

- `POST /api/marketplace/oauth/bootstrap`
- `GET /api/marketplace/oauth/authorize`
- `POST /api/marketplace/oauth/token`
- `POST /api/marketplace/oauth/refresh`
- `GET /api/marketplace/logistic/channels`

## Roles and Permissions

Order actions are restricted both in the backend and reflected in the frontend:

- `picker`: can run `pick`
- `packer`: can run `pack`
- `warehouseAdmin`: can run `ship`
- `superAdmin`: can run all actions

The frontend reads the role from JWT and disables unauthorized actions in the UI. The backend remains the source of truth by enforcing permissions through role-based middleware.

## Error Handling

The backend already handles several important cases:

- invalid request body -> `422`
- unauthorized / invalid token -> `401`
- user already exists -> `409`
- order not found -> `404`
- invalid status transition -> `400`
- incomplete marketplace configuration -> `400`
- marketplace request failures -> mapped to `502` or `500` depending on the case

The marketplace repository also includes retry logic with backoff for external requests, making the integration more resilient to random failures from the mock API.

## Running the Project

### Prerequisites

- Go `1.22+`
- Node.js `18+`
- PostgreSQL
- `migrate` CLI for database migrations

### 1. Backend setup

Go to the backend folder:

```bash
cd backend
```

Copy the environment file:

```bash
cp .env.example .env
```

Minimum `.env` content:

```env
# Server Configuration
SERVER_HOST=localhost
SERVER_PORT=9000

# Database Configuration
DB_HOST=localhost
DB_PORT=5432
DB_NAME=wms-marketplace
DB_USER=postgres
DB_PASSWORD=postgres
DB_TZ=Asia/Jakarta

# JWT Configuration
JWT_KEY=secret
JWT_EXP=10

# Marketplace Configuration
MARKETPLACE_BASE_URL=
MARKETPLACE_PARTNER_ID=
MARKETPLACE_PARTNER_KEY=
MARKETPLACE_SHOP_ID=
MARKETPLACE_REDIRECT_URL=
```

Notes:

- marketplace fields are not yet included in `.env.example`, but they are required by the backend config loader
- without a complete marketplace configuration, sync, logistic channel lookup, OAuth, and ship-to-marketplace flows will not work fully

Run migrations:

```bash
make migrateup
```

Run the backend server:

```bash
make run
```

Backend default address:

```text
http://localhost:9000
```

### 2. Frontend setup

Go to the frontend folder:

```bash
cd frontend
npm install
```

Run the frontend dev server:

```bash
npm run dev
```

Frontend default address:

```text
http://localhost:5173
```

By default, Vite proxies `/api` requests to `http://localhost:9000`.

## How To Test the Main Flow

### Operator flow

1. log in using one of the seeded accounts
2. open the order list
3. select an order to see its detail
4. run the action that matches the current role and order status

Status to action:

`READY_TO_PICK` -> `pick`  
`PICKING` -> `pack`  
`PACKED` -> select a logistic channel and run `ship`

### Ship flow

When the ship action is triggered:

1. the frontend sends `channel_id` to the backend
2. the backend validates that the order is currently `PACKED`
3. the backend calls the marketplace endpoint `/logistic/ship`
4. the backend persists `shipping_status` and `tracking_number` from the marketplace response
5. the backend updates `wms_status` to `SHIPPED`

This flow follows the technical test requirement that tracking numbers must come from the marketplace.

## Important Implementation Notes

- The backend is the source of truth for authentication, authorization, state transitions, and marketplace token storage.
- The frontend improves usability, but the backend performs the actual enforcement.
- Orders are only created locally when they are relevant for WMS processing.
- The raw marketplace payload is stored to help with auditing and troubleshooting.
- Webhooks are public because they follow external integration patterns, while internal APIs remain protected by JWT.

## Current Gaps / Next Improvements

Some areas that can still be improved:

- document response payloads more explicitly for each endpoint
- add Docker-based local development setup
- add automated tests for service and API layers

## Summary

This project already provides a solid baseline for a simple WMS:

- the backend handles auth, order lifecycle, synchronization, webhooks, and marketplace OAuth
- the frontend provides a focused outbound operations UI
- the design keeps marketplace responsibilities separate from WMS responsibilities

This README is written based on the current implementation in the repository, not only on the original technical test brief.
